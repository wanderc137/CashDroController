El concepto

Qué es y por qué existe

El problema, el enfoque y el alcance real del proyecto.

CashDroController es una aplicación de consola en Python para Windows que opera un reciclador de efectivo CashDro mediante su API REST sobre HTTPS, sin SDK ni puerto serie. Permite fijar un importe, abrir una venta, sondear hasta que el cliente introduce el efectivo, mostrar ingresado, devuelto y cambio, anular con el operationId y consultar niveles, alertas y diagnóstico. Apunta a cajeros y técnicos que ya tienen el equipo y necesitan un mando mínimo desde un PC.

Demuestra un cliente sobrio: normalización del JSON en el borde, reintentos separados para el error de aplicación (-1900) y el de transporte, Ctrl+C que cancela en vez de abandonar, y marcadores en lugar de credenciales. No hace contabilidad, cierres de caja, tickets ni catálogo, y no está validado contra hardware: se escribió contra el manual v22.01.21.11 y solo se probaron sintaxis, simulaciones HTTP y auditoría estática.

Cómo leer esta ficha

Los tropiezos salen de la bitácora y de las versiones tempranas. La evaluación usa seis criterios fijos, de 1 a 5, y no premia la espectacularidad: premia que el proyecto se pueda reproducir y entender.

01 — La idea

El efectivo también necesita una API

Un CashDro no es una caja registradora: es un periférico con estado, niveles y operaciones asíncronas. Esta consola lo opera sin esconder esa complejidad.

El problema

Las operaciones con efectivo tienen estados intermedios: la máquina acepta, clasifica, recicla y confirma. Una integración naive consulta una vez y asume que todo salió bien. El resultado son descuadres y tickets sin sustento.

La solución

Una consola que modela el ciclo completo: autenticación, venta, polling de estado, reintentos ante System busy y consulta de niveles. Cada operación deja un resultado legible para el operador.

03 — Bajo el capó

Una consola, un protocolo

La lógica de negocio vive en la consola; el CashDro solo expone su API.

Polling con timeout

No se asume éxito: se consulta el estado hasta una condición final o un límite de tiempo.

Reintentos selectivos

Solo los errores recuperables, como System busy, se reintentan.

Operación visible

Cada paso se muestra en la consola para que el operador sepa qué está pasando.

Tropiezos

Los tropiezos, documentados

Lo que no funcionó en las primeras versiones, con la corrección aplicada.

v1.0 · primera auditoría

operation_id sin inicializar

Un fallo temprano en startOperation producía UnboundLocalError al entrar en el except que intentaba cancelar, porque la variable se asignaba dentro del try. Se inicializó a cadena vacía antes del try y se comprueba su valor antes de llamar a finish_operation.

v1.0 · reintentos

System busy (-1900) terminaba como error de red

El -1900 se lanzaba como CashDroError, pero el except solo capturaba excepciones de requests y el mensaje final era "Error de conexión tras 3 intentos: None". Se separó un contador system_busy_retries_left con espera de 5 s; al documentarlo se vio que comparte iteración con el bucle, así que el máximo real son 3 peticiones y no 6.

v1.0 · máquina de estados

El estado E (ejecutando) se trataba como error

La lista de estados válidos durante el sondeo omitía E, de modo que la operación abortaba justo cuando el equipo empezaba a ejecutarse. Se aceptan I, Q, E y cadena vacía; solo F finaliza y cualquier otro valor es error.

v1.0 · publicación

IP y credenciales de ejemplo en el repositorio

Los datos de la instalación de desarrollo quedaron en config.py y en el script de lanzamiento. Se movieron a variables de entorno con marcadores (192.0.2.10, USUARIO_CASHDRO, CLAVE_CASHDRO); cashdro.sh sigue con valores de ejemplo y quedó como pendiente explícito.

Preguntas

Lo que suelen preguntar

¿Qué es CashDroController?

Una aplicación de consola en Python para Windows que cobra, anula y consulta el estado de un reciclador de efectivo CashDro a través de su API REST sobre HTTPS, sin SDK propietario.

¿Administra caja, stock o facturación?

No. Solo mueve el importe que teclea el operador y devuelve el resultado; no hay catálogo, cierres de caja, arqueos, histórico ni impresión de tickets.

¿Cómo se ejecuta?

Se crea un venv, se instala requests, se definen IP, usuario y contraseña por variables de entorno y se lanza python main.py; antes conviene comprobar con curl -k que doTest responde code:1.

¿Qué se puede reutilizar?

La clase de API con normalización de JSON y reintentos, el manejo de Ctrl+C como cancelación y el patrón de configuración por variables de entorno con marcadores públicos.
